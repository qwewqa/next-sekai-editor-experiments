# Next SEKAI Editor

Next SEKAI Editor is a free, open-source chart editor for the Sonolus rhythm game engine.

[Open the Editor](https://nse.qwewqa.dev/)

[Release Notes](CHANGELOG.md) · [Usage Statistics](docs/usage-statistics.md)

## Local Development

Use the Node.js version in `.node-version`.

```sh
npm ci
npm run dev
```

### Preview Assets

The web editor uses the Next SEKAI skins, particle effects and sound effects from
coconut.sonolus.com. The packages are listed in `deployment/preview-assets.lock.json`.

Before starting the dev server, `npm run dev` prepares the packages in `public/resource/`.
It keeps packages that match the lock file. For missing or outdated packages, it uses
a matching copy from `node_modules/.cache/nse-preview-assets/` or downloads and verifies
the package against the lock file.

To update the packages, run `npm run refresh:preview-assets`. This rewrites the lock file
from items on coconut.sonolus.com. To use a different Sonolus item, set
`PREVIEW_<NAME>_URL`, where `<NAME>` is `SKIN`, `SKIN2`, `PARTICLE`, `EFFECT` or `EFFECT2`.
Commit the updated lock file.

If a package is still missing or does not match the lock file, the dev server prints a
warning and the editor uses only the Built-in assets, as the native build does. To use
only the Built-in assets during development, run `NSE_SKIP_PREVIEW_ASSETS=1 npm run dev`.

To prepare the packages manually, as CI does:

```sh
node --input-type=module -e "const { stagePreviewAssets } = await import('./scripts/release-assets.mjs'); await stagePreviewAssets(process.cwd(), 'public')"
```

`npm run build:release` builds `dist` with the preview assets.

## Built-in Assets and the Native Build

The Built-in assets in `public/builtin/` are generated from `builtin-assets/`
with `npm run build:builtin-assets` and committed to the repository.
`npm run check:builtin-assets` rebuilds them and compares the generated bytes with the
committed files.

`npm run build:native` builds the frontend for the apps in `dist-native/`, using a
temporary public folder containing only files on the allowlist.
`npm run check:native-bundle` checks the result for web-only files and references.
Neither command requires Rust.

## Browser Compatibility

The minimum supported versions are Chrome 111, Edge 111, Firefox 128, Safari 17 and
iOS 17.

The editor requires IndexedDB, `navigator.storage.estimate`, Web Locks,
OffscreenCanvas and `structuredClone`, and its stylesheet requires `color-mix()` and
`CSS.registerProperty`. At startup, `public/gate.js` displays an unsupported-browser
page if any of these are unavailable.

For syntax, the production build targets Chrome 111, Edge 111, Firefox 128,
Safari 16 and iOS 16. When updating Vite, keep these targets set explicitly in the
Vite configuration. Vite’s [default build targets](https://v8.vite.dev/config/build-options)
can change between major releases.

For other browser APIs, the editor uses feature detection or fallbacks. Notes are drawn
without `roundRect` when it is unavailable.

```sh
npx playwright install firefox webkit
npm run test:compatibility
```

This builds the production UI and runs compatibility tests in Firefox, WebKit and
mobile WebKit. They cover:

- importing, exporting, touch context menus and scaling;
- elevation layouts in portrait and landscape;
- WebGL rendering in the editor;
- decoding and rendering preview textures;
- internal copy and paste when clipboard permission is denied;
- audio scheduling and waveform rendering.

Older Playwright releases provide archived binaries at the minimum versions:
Chromium 111 (Playwright 1.31.2), Firefox 128 (1.46.1) and WebKit 17.0 (1.37.1). They can
run the production UI checks. Below the minimum, Playwright 1.27.1's Chromium 107 and
Firefox 105 display the unsupported-browser page. Use these older binaries only in a
separate local test setup, with its own `PLAYWRIGHT_BROWSERS_PATH`.

[Playwright WebKit](https://playwright.dev/docs/browsers#webkit) is a build of the browser
engine used by Safari. Test Safari itself separately, including iOS Safari on a physical
device for audio activation, clipboard permissions, file pickers and downloads,
toolbars that resize the viewport, and safe areas.

Windows WebKit lacks Web Audio, so audio tests are skipped there. The production UI
tests use an audio stub on Windows and skip WebKit builds that lack OffscreenCanvas.
Linux CI runs the audio tests without the stub.
