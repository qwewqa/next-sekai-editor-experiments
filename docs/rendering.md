# Renderer ownership and upgrades

## Chosen stack

The editor couples directly to pinned Pixi WebGL2 resources, ordered batches and retained geometry. It does not expose interchangeable rendering backends. The editor, preview and cover sampler require WebGL2 and fail clearly when its context cannot be created. Pixi supplies resource management and batching; the editor owns the smaller set of path, coverage and text contracts that its chart artwork needs. Default Pixi Graphics cannot reproduce compound translucent fills/strokes by itself, so those operations use the explicit union/coverage paths below. Replacing Pixi with a custom sprite renderer would still leave those correctness and lifecycle responsibilities.

The small Rust/Lyon fill kernel accelerates supported contour unions through one bulk numeric call. It does not own WebGL, replace browser font shaping or duplicate the editor's curve flattening. Its precision guards and unchanged JavaScript fallback are part of the rendering contract. See [`native/lyon/README.md`](../native/lyon/README.md) for the pinned toolchain, binary/source verification, memory/failure model and dependency notices. Ordinary JavaScript builds use the checked-in verified binary and need no Rust installation. Initialization never delays the first editor draw; existing cached JavaScript geometry remains valid when acceleration becomes available.

Very wide hovered notes can produce thousands of dash pieces in one rectangular outline. For certified separated rectangle dashes, straight middle pieces use direct triangles; corner pieces and the first/last pieces still share the existing union, preserving single-coverage alpha at the closed seam. Unsupported stroke styles or geometry keep the general union. Keep the wide-rectangle and seam-overlap regressions when changing this path: a short chart-drawing callback does not exclude a stall in the separate hover overlay.

The existing preview keeps its direct WebGL2 renderer and GLSL ES 3.00 shaders. Its workload already fits that renderer; forcing it through the editor's retained scene machinery would add a separate migration without an established benefit. Both renderers still share the editor's explicit ownership and restore requirements where they use common surfaces.

A preview frame's work tracks the notes in view, not the rest of the chart. [`frameIndex.ts`](../src/preview/engine/frameIndex.ts) indexes notes, connectors and simultaneous lines under each time scale group their progress depends on; each frame asks [`latestTargetWithin`](../src/preview/engine/timescale.ts) for the latest target whose distance can still be within the approach window, and later entries are skipped. The bound walks the group's changes from the current time only until per-change suffix bounds on the distance put the rest out of reach, so stops, backward speeds, negative skips and scroll transitions stay exact; it keeps a small slack, so it can only include extra entries. It is an upper bound only: connectors and attached notes can show while their endpoints lie on opposite sides of the view, so entries far behind the judge line stay candidates. While a scroll segment's speed is negative, or one runs into a time scale stop that later skips backwards (coconut before 114 s: the scroll ratio into the stop is about 11,000), most of the group's future is in reach and the frame processes it. `frame-index.test.ts` compares culled and full-traversal frames on real charts, including every stop and scroll transition; set `PREVIEW_CULL_CHARTS` to add local dense charts. The selection sets the preview highlights are built when the selection changes, not per frame.

A frame's cost includes its candidates as well as what it draws, and most candidates draw nothing. On the opening of coconut-next-sekai-23792 the bound admits about 700 connectors and 1,500 notes a frame, and about 7 of them are in view. A candidate's progress alone decides whether it can be in view, so the frame tests that first and builds lanes, stage transforms and masks only for the rest. Connectors, notes and simultaneous lines each repeat the progress test of their draw function ([`render.ts`](../src/preview/engine/render.ts)). A frame then costs a progress lookup per candidate, plus the geometry, particles and draws of what is in view. Dense passages cost several times more than openings. A frame computes stage values only for the stages it uses.

[`chart.ts`](../src/preview/engine/chart.ts) builds the notes and connectors in time order. Items with equal times keep the order of their slides in the slide info map, and an edit can change that order. An edit merges the notes and connectors of the slides it changed into the order of the previous build. A change to the BPMs, time scales, groups or the set of stages rebuilds every slide. If two unchanged slides have notes at the same time and have swapped places in the map, the build sorts all notes and connectors again. The result equals a full build, element for element. `chart-incremental.test.ts` checks this over random edits, undo and redo.

Per-frame code must not build objects with the same function or literal as long-lived data. V8 tracks each allocation site, and once most of a site's objects survive, V8 allocates every later object from that site in the old generation, where only a major GC frees it. The time scale groups build their long-lived transfer tree through a literal of their own ([`timescale.ts`](../src/preview/engine/timescale.ts)), not through the helpers that frames call. Built with those helpers, the tree made playback of a dense chart run a 4–7 ms major GC once or twice a second.

The preview's selection outline is drawn on its own overlay canvas by a small WebGL2 renderer ([`outlineRenderer.ts`](../src/preview/outlineRenderer.ts)), and its edges move every playback frame. It draws each edge as its body and two round caps ([`strokeSegments.ts`](../src/rendering/strokeSegments.ts)): flat opaque triangles, a dark 5 px stroke under a 2 px cyan one, with the default framebuffer's MSAA and no path or cache entry. Stroking the edges as a path would tessellate and cache a new path twice a frame. With every note selected, that cost 7–11 ms. The caps have the points that a stroked path's caps have, at the path cache's tolerance for the current transform, so the overlapping triangles cover what the path's union covers. `previewOutline.spec.ts` compares the renderer with the editor's stroked path at several device scales: interiors are identical, and an edge pixel differs by at most two of four MSAA samples, where the union moves slanted edges by a few hundredths of a pixel. The renderer imports nothing from the editor's context, so the preview's worker can use it too. It creates its context only when something is selected, and after a context loss it draws its last frame again. A stage with a selected stage transform event also gets an X 12 px across at its rotation centre. The X turns with the stage and is drawn after the outline in the same strokes, so its dark stroke separates it from the lines under it.

## The preview draws on the main thread or in a worker

The preview has two hosts. Both draw a frame with [`drawPreviewFrame`](../src/preview/drawFrame.ts): the same engine, renderer and outline renderer. [`usePreviewRendering`](../src/preview/usePreviewRendering.ts) decides what each frame shows in either: the chart request, the selection, the sizes, the settings and when to draw.

`drawPreviewFrame` returns `{ drawn: true, backgroundQuad }` after drawing, or `{ drawn: false, reason, backgroundQuad }` for a lost context (`context`), missing skin or atlas (`resources`), invalid dimensions (`size`) or a drawing exception (`error`). While replacement atlases load, a host can draw a partial frame and receive `drawn: false` with reason `resources`. The background quad stays in both results. The hosts remove the first-paint placeholder after a frame is drawn. A caller that needs every frame must check it.

The renderer draws the foreground into an offscreen target ([`renderTarget.ts`](../src/preview/renderTarget.ts)). `setRenderTarget` allocates a single-sample RGBA8 texture, with a 4-sample renderbuffer when antialiasing is on. It reuses the target while its dimensions and antialiasing stay the same and frees it when replaced or when the renderer is disposed. Every framebuffer is checked for completeness at allocation; failure throws. Each panel frame uses a target at its drawing-buffer size, with the panel's Antialiasing choice.

For a target, the frame's width and height are the render dimensions. After drawing, `resolve()` copies the MSAA buffer into the texture at the same size. WebGL2 cannot scale during an MSAA resolve. `present(width, height)` draws the resolved texture into the canvas at the output dimensions. Its shader averages the source area covered by each output pixel, including fractional coverage at 1.5x, and preserves premultiplied RGBA. At 2x it averages four texels; at 1x it copies one. Resolve and presentation are separate so a caller can composite the foreground before downscaling. After all passes, `checkError()` checks for a GL error or a lost context. These checks stay off the panel's frame path. `previewRenderTarget.spec.ts` compares the output with area averages computed on the CPU of an independent draw at the render size, with antialiasing on and off.

- **The main host** draws on the main thread into the panel's canvases.
- **The worker host** draws in a worker that lives as long as the page ([`preview.worker.ts`](../src/preview/worker/preview.worker.ts)). The panel transfers its two canvases to it (`transferControlToOffscreen`), and a frame reaches the screen when the worker's task that drew it ends. It runs while Settings › Preview › Parallel Rendering (`previewInWorker`) is on, as it is by default, in a browser with `Worker`, `OffscreenCanvas` and `transferControlToOffscreen`; elsewhere the switch is not shown. Changing the setting moves the preview between hosts at once, and the panel's canvases are mounted again. The test key `nse.test.previewHost` (`main` or `worker`) overrides the setting. Release builds do not read the key; perf builds do, so one build can measure both hosts.

The main side of the worker host ([`host.ts`](../src/preview/worker/host.ts)) sends the worker what it draws:

- **The chart:** a copy of what the builder reads (`PreviewChartSource` in [`chart.ts`](../src/preview/engine/chart.ts)), sent as a diff by identity ([`mirror.ts`](../src/preview/worker/mirror.ts)). The first copy goes at open and after a chart switch. After that, only the fields, event grids and slides whose identity changed are sent, each slide with its connectors in one clone so they share their notes, together with the order of the info map's keys. The copy's unchanged slides keep their identity, so the builder's per-slide cache and its merge of changed slides work as on the main thread, and the same key order breaks ties the same way. `mirror.test.ts` builds the copy's chart and the main thread's after random edits, undo jumps and chart switches, and compares them element by element and by what they draw.
- **The selection:** each selected note and connector as its slide id and index in the slide. Entities have no ids, and the worker's copies are other objects.
- **Each frame:** the time, the left limit, the sizes, the note speed and the display settings. The main thread keeps the clock. At most one frame is in flight, and a newer request replaces a frame that is still waiting. So a slow frame lowers the preview's frame rate, and each frame that is drawn still shows the current time.
- **The images:** the skin and particle atlases and the background bitmap are transferred, not copied. The worker keeps them for the page's life and uploads them to each new context. A replacement closes the old bitmap. During handover it returns them to the main host; if the worker cannot return them, the asset session decodes them again.

Both hosts draw the background in the renderer. Pass A draws the scene and combo into the transparent foreground target, with the existing normal and additive blending. After resolving that target, pass B clears the canvas to the background colour over the theme backdrop. It draws the image in slot 3 on the engine's background quad, then the mask, then the foreground with premultiplied source-over (`ONE, ONE_MINUS_SRC_ALPHA`). This preserves the attenuation of the background under additive particles. The main thread reads the backdrop from the theme token and passes its RGB channels in the frame input. A caller that holds the input keeps that colour across theme changes. The backdrop is black when no backdrop is supplied or no background is loaded. The selection stays on its own canvas. Only the default image's first-paint placeholder uses CSS; there is no per-frame DOM transform.

[`backgroundPass.ts`](../src/preview/backgroundPass.ts) blurs the image before its camera transform. With sigma in output pixels, the working scale is `min(1, 8 / sigma, 2048 / longest padded side)`. Before the blur, area averaging reduces the source by at most 2x per axis per pass. The final copy also averages its source area and adds a transparent three-sigma margin. These reductions and the two separable Gaussian passes reuse at most two 2048-square RGBA8 textures (32 MiB). The working sigma is at most 8 pixels. The blurred texture uses linear filtering and its quad includes the margin. Blur 0 uses the original image without a copy.

The blur cache belongs to the renderer. Its key includes the bitmap, working dimensions, sigma and padding. Changing resolution or blur replaces the cached pixels. The frame input carries sigma in drawing-buffer pixels, computed directly from the held display height. While a panel is being resized, the drawing buffer and sigma stay fixed until release. The bitmap remains available for context restoration. `previewBackground.spec.ts` checks the composite equation, compares a resized blur with a fresh copy and checks detailed stripes against their average at maximum blur at 2160p. `preview.spec.ts` checks that resizing through fractional panel heights reuses the blur and its allocations in both hosts. The Elevation panel builds its own chart on the main thread.

[`copyPreviewAtlases(signal)`](../src/preview/copyPreviewAtlases.ts) makes independent copies of the shown skin and particle textures, with their sprite data and interpolation settings. It uses the asset session's loading and fallback rules even when the preview has never opened. The main thread copies local bitmaps; the preview worker copies bitmaps it holds and transfers only the copies back. Originals stay with their owner. The result is `copied`, `failed` or `cancelled`; a failed particle load permits a skin-only result, as in the preview. Loading and copying have no deadline. They continue through reloads and handovers between hosts until they finish, fail or the caller cancels. An asset or host change restarts copying. Cancellation, failures and restarts close partial or late copies. The caller closes every texture in a successful result.

When the worker host fails, it hands over to the main host for the rest of the page's life, whatever the setting says. It shows no notice and records the reason for Copy Diagnostic Info: the worker could not create a WebGL2 context, it threw an error, or it did not respond within 10 s. A worker that still responds hands the atlases back; otherwise the skin and particle are decoded again. The worker's canvases keep its last frame until the main host draws its first. A context lost in the worker is restored there, as on the main thread. `previewWorker.spec.ts` forces each handover, and compares the two hosts' pixels. WebKit allows WebGL in workers only on Apple's platforms. On other platforms, such as Linux, the worker cannot create its context and hands over as soon as it starts.

A canvas's context in the worker is released only two animation frames after the canvas left the page. A replaced canvas, such as the old one after an Antialias change, keeps its context until the main thread sends `release`. A stopped worker that still responds keeps its canvases, and is terminated only after the main host has drawn and two more frames have passed. A worker that does not respond is terminated at once. In Firefox, releasing the context sooner, or terminating the worker while the page still shows its canvas, could stop the page from painting until the next input, or hang the worker until the 10 s limit. `previewWorker.spec.ts` holds the page's animation frames, and checks that neither the release nor the termination happens before they run.

## Playback sound

[`playerSounds.ts`](../src/playerSounds.ts) owns the pure sound rules. `planSounds` takes chart entities, BPMs, clip availability, a window in chart seconds and the previous spacing state. It collects events from `planHits` and `planHolds` to return hit times, visible hold pieces and the next state. `planHits` returns the next spacing state when its iterator ends. `planActiveSound` checks one voice at a time for expiry, overlap and extension, using the current audio time.

[`playerSoundScheduler.ts`](../src/playerSoundScheduler.ts) owns each playback's nodes, continuation state and indexes for slide info and hidden sections. It maps chart time to audio time, schedules ahead and checks the audio clock again before starting each sound. It queues each hit clip before planning the next clip, then scans hidden sections and holds. It queues each hold before converting the next hold's times. This keeps later planning from delaying nearby sounds on a restart without preroll. The grid traversal comes from `state/store/grid.ts`, shared with History. `playerAudio.ts` applies hold decisions and owns gain ramps, loops and node cleanup. It releases each expired voice before checking the next voice against the audio clock.

`player.ts` owns Play's context, decoding, timer and stall recovery. Its scheduler does not depend on drawing frames. Stop and volume changes affect only that scheduler's nodes. `tests/editor/playerScheduling.test.ts` compares Play's calls with recordings from before this split; the browser playback specs also exercise the native audio clock.

## Ownership and draw boundaries

[`src/rendering/context.ts`](../src/rendering/context.ts) is the editor's drawing API, not a complete Canvas2D compatibility layer. `getDrawContext(HTMLCanvasElement)` creates one `WebGLDrawContext` and one `RenderingResources` owner per root canvas. `createSurface()` creates a `RenderSurface` with its own drawing state, target, path cache and node pools, sharing the root's WebGL renderer and image cache. `drawImage(RenderSurface)` requires this shared owner; cross-owner targets are rejected.

`WebGLDrawContext.flush()` submits queued nodes and detaches/recycles them. `clear()` starts a new image; later flushes append without clearing. Reader dependencies, sampler changes, image eviction, layer completion and readback can cause a flush before the caller's final presentation. So `RenderingResources` requires `preserveDrawingBuffer: true` and `clearBeforeRender: false`: changing these flags alone can discard earlier root pixels between incremental submissions or before delayed readback. An atomic full-frame renderer would require a different lifetime contract and corresponding reader/readback tests.

Only the editor schedules frames and handles DOM input. [`src/rendering/resources.ts`](../src/rendering/resources.ts) replaces Pixi's `EventSystem` and `SchedulerSystem` registration. Keep Pixi GC enabled: native resource cleanup and managed-collection compaction are both needed after a long idle. A GC pass walks every tracked resource, so its cost follows what is live: 10–20 ms at 1x late in a session, up to 60 ms at 4x CPU throttle. [`RenderingScheduler`](../src/rendering/scheduler.ts) therefore runs GC's tasks and its pass at idle time (`requestIdleCallback`, or a timer where there is none), never inside a frame:

- once a task is due and no renderer has rendered for 1 s;
- while renders go on with no such pause, at the next idle period 60 s after the due time or after those renders began, whichever is later;
- only within 30 s, half of GC's 60 s unused time, of its own renderer's last render, so a pass never unloads what that render used. After that, the renderer's next render arms it again.

It requests no animation frames and schedules nothing before a render. Playback redraws the chart every frame, so it counts as rendering. With Elevation open alone and no selection, no Pixi renderer draws during playback, so Elevation's own small pass can run between preview frames. `GC_FREQUENCY` (10 s, in `resources.ts`) sets the period; each pass unloads the resources unused for 60 s.

Focus and toolbar jumps farther than two full viewport time spans go directly to their destination and cancel the pending vertical animation. This intentionally avoids constructing unseen intermediate chart sections during a long jump. In-view focus stays put and shorter focus pans retain their 0.25-second ease. The threshold uses the full viewport height divided by PPS, including the area before chart time zero; invalid or zero viewport spans keep the ease. The rule covers only focus and toolbar jumps, not manual scrolling, touch inertia, pinch or the transport.

## The app clock runs only while something moves

[`src/time.ts`](../src/time.ts) drives motion: eased scrolls, inertia, playback, a tool drag's update and edge pan, and a held preview step. It ticks once per animation frame, and only while one of these needs it. An idle editor requests no animation frames, so the GPU and compositor can sleep. A clock that ticks on every frame costs 7–11% of a core on a 240 Hz display.

- **Needs.** Each consumer registers what it needs with `keepClockWhile(need)`: the view's eased and inertial scrolls (`view.scrollingX`, `scrollingY` and `scrollingPane`), the transport's playback, a tool drag (`isDragging`), and a held step until it ends. The need is reactive: when it turns true, the clock wakes in the same task. The clock stops after the tick whose watchers leave nothing needing it, such as an ease reaching its end.
- **History's flush** holds the clock while it extracts a step in slices (`storing.ts`). Each slice runs in an idle period, and an idle callback asked for inside another runs only in the next idle period. Frames bring an idle period every frame. Without them, idle periods come about 50 ms apart, and a flush of 150 steps takes 7 s instead of 2.6 s at 60 Hz.
- **Reading the time.** `time` is the last tick. Start times and gesture samples read `clockNow()`: the last tick's time while the clock runs, else one frame before now, where a running clock's last tick would be. The first frame after a wake then moves by about one frame, as every later frame does. A stopped clock's `time` would give every sample of a pan the same time and fling it with the whole gesture's distance.
- **Recently active** (`isViewRecentlyActive`, the note outlines' active variant) ends on a 0.5 s timer, not on a tick.
- **What runs without it.** Direct scrolls (a pan, the quick-scroll zone, a minimap drag, a wheel without smooth scrolling) move the view in their input handlers, and the canvases draw in their own animation frame. The minimap, the preview, notices, the GC pass and the idle compile use their own frames, timers or idle callbacks.
- **A new consumer** that moves on `time` must register a need, or it freezes until something else wakes the clock. So must a chain of idle callbacks that counts on one idle period a frame. `tests/browser/frameClock.spec.ts` checks that an idle editor does not tick, that an eased scroll, playback and a quick-scroll flick each wake the clock and end, and that a History flush runs it.
- A wake's first tick can follow a draw that an earlier input in the same frame requested, so that frame draws twice. Both draws finish before the frame is shown.

## Images, readers and destruction

`RenderingResources.image()` caches immutable `HTMLCanvasElement`, `HTMLImageElement` and `ImageData` sources by identity. `ImageData` gets an owned premultiplied byte copy; DOM image uploads use Pixi's premultiply-on-upload mode. ImageBitmap is intentionally not part of this renderer's image-source contract.

Every queued image draw registers a texture-source reader. Before changing a target's pixels, replacing its sampler or deleting an uploaded image, flush its readers. `releaseImage(source)` performs that synchronization before destroying its texture. A producer may then change or shrink the source canvas. Do not mutate a cached source in place and expect another draw to upload it. Crop textures in `WebGLDrawContext.frames` borrow the source; destroying a crop must not destroy the source.

Immutable `NoteAtlasRegion.texture` metadata instead belongs to its atlas slot/page. It borrows the page surface's source, flushes readers before normal destruction and destroys only the metadata with `destroy(false)`. Source destruction or a changed renderer-owner identity invalidates it. A page releases all regions before disposing its surface; these regions are not owned by `WebGLDrawContext.frames`.

Domain caches own their sources and release them explicitly: see [`labelSprites.ts`](../src/editor/canvas/labelSprites.ts), [`waveform.ts`](../src/editor/canvas/waveform.ts) and [`noteAtlas.ts`](../src/editor/canvas/noteAtlas.ts). The general native-text raster cache instead drops immutable CPU references on eviction; another renderer may still own an uploaded source, so those canvases must not be cleared during CPU-cache eviction.

`RenderSurface.dispose()` releases only that surface. Root `disposeDrawContext()` releases all clients, queued/layer targets, node pools, geometry, paints and image textures, then destroys the Pixi renderer and loses its native GL context. Initialization is asynchronous: await `ready` before synchronous export/readback; editor drawing waits for `isReady` and `renderingready`. Disposal during initialization is deferred until the init promise settles.

On context loss, draws stop. Restoration waits until Pixi has reset its native maps, invalidates all cached texture bindings, replaces the `resourceOwner` identity and resets client surfaces. The editor must redraw after `renderingready`; old pixels are not retained. Domain caches use owner identity to invalidate native handles. Keep the texture-binding reset: a restored renderer with more than sixteen texture units otherwise reused stale bindings in the first redraw.

Renderer-owned Vue canvases must invalidate their retained caches on `renderingready`, not the earlier native `webglcontextrestored` event. Their native listener can run before Pixi's asynchronously registered listener and delete buffers from the old context generation. The independent preview renderer still handles its own native restoration lifecycle.

## Geometry and retained scenes

`PathGraphicsCache.destroy()` is final owner teardown, not a live-context invalidation API: retained groups must release their pins and readers before the owning context destroys its path cache.

[`PathGraphicsCache`](../src/rendering/pathGraphics.ts) owns native `GraphicsContext` and `PathMeshGeometry` resources, keyed by recorded commands, style and device resolution. Frame transitions visit only the preceding frame's touched entries. An eligible LRU heap orders unpinned, non-current entries by their actual last access; releasing a pin preserves that access order. Current-frame geometry cannot be evicted while queued. Retained scenes use `pin()`; an over-budget capture is declined rather than retaining temporary geometry indefinitely. Destroy scene nodes before releasing their geometry pins.

Only paths a caller keeps and passes again are reused across frames: connector bodies and edges, fake markers, event paths and ease glyphs, and the context's keyed rectangles, lines and circles. A context's current path (`beginPath()`, then `fill()`, `stroke()` or `clip()`) is a new object in every frame, so its geometry is frame-only: it never enters the LRU, and it is released once its frame is presented, or once the last retained scene pinning it lets go. Paths rebuilt every frame, such as the grid lines and the cursor line, would otherwise fill the budget with geometry nothing draws again. Chart frames would then stall for 10–20 ms during playback, on the cache's grown maps and on garbage collection.

Installing another chart (New, Open, Restore Session, a reopened or recovered session: every path that calls `notifyResetState`) runs `releaseUnusedPaths()`, registered in [`surface.ts`](../src/editor/canvas/surface.ts), on every live draw context, render surfaces included. Each cache releases its unpinned entries at once. Pinned and queued entries stay, and each goes at the first frame boundary that finds it unpinned, unless a draw of the new chart used it again by then. Without this, a switch would keep up to the whole 128 MiB budget of the old chart's geometry. Paint ramp references follow geometry destruction in [`pixiPaint.ts`](../src/rendering/pixiPaint.ts).

[`sections.ts`](../src/editor/canvas/sections.ts) partitions the complete source-ordered chart into stable 4-beat sections. Its source chunk index relies on immutable `Map`/bucket `Set` identities: replace changed collections rather than mutating them in place. Selection differences rebuild the affected type/chunks, including non-notes. Chunks cache their member chain keys; only a change to a member chain's raised state reprojects that chunk, while swaps within an already-raised chain update only the directly highlighted chunks. Source replacement refreshes those memberships. Changed point buckets stay local; structural changes to spanning families and shared visibility/order changes retain conservative broader rebuilds. Published sections remain immutable, and visibility/nested-chain inputs are still read on every build to preserve reactive dependencies. Sections compile when first visible, or earlier at idle time (vector sections, below), and may remain resident offscreen. A pan changes the visible plan without changing a section's membership. Ambiguous ordering ties use the existing visible-sequence path. Names, labels and hit testing still use visible entities; long connections retain their original painter order.

[`VectorRanges`](../src/editor/canvas/vectorRanges.ts) retains consecutive, order-preserving vector sections and the existing visible ranges used by live previews. `captureVectors()` owns the group and geometry pins; `drawVectors()` changes translation only and rejects a changed owner or linear transform. Names remain separate metadata. Membership, painter order, selection, shared style inputs and immutable entity edits are part of validity. Active sections are protected before any new capture. Pressure reclaims inactive sections; a declined capture draws once instead of immediately repeating its construction. `endFrame()` releases departed visible ranges and one-shot captures after the caller flushes, while reusable sections may remain offscreen. `releaseVectors()` also flushes a directly queued range before destruction. Do not put arbitrary unowned image sprites into these vector captures.

Vector sections within one view span of the view are compiled at idle time, nearest first, so a scroll reaches them warm. After a frame that drew sections, `endFrame()` asks for an idle callback (`requestIdleCallback`, or a short task where there is none). It captures with that frame's context and draw callback, under the frame's transform, and only when the context's drawing state equals the one the frame captured in, so an idle capture is the one the frame would have made. Each capture is started only when the idle time left fits its estimate, a running average of recent captures; an idle period of 40 ms fits any. With the app clock stopped, an idle period lasts up to 50 ms, so after its first capture a callback starts another only while the estimate fits within 8 ms of the callback's work. It then asks for the next callback from a timer task: one asked for inside an idle callback waits for the next idle period, about 50 ms away when no frames come. One capture can still take longer than 8 ms, and such a section is still compiled ahead: at 4× on 21888 zoomed out, the longest idle task before an input was 7–20 ms. While the app clock runs, every idle period ends before its next frame, so asking again at once after one too short for the nearest section would spin. The pass tries again 100 ms later, up to ten times in a row, and then waits for the next frame that draws sections. Eviction for it takes only sections outside the view and that span, and a capture that does not fit is released. That ends the pass until the view or plan changes. After a frame that changed UPS (a zoom), the pass waits until 250 ms pass with no frame, since the next zoom frame would release what it compiled. Idle captures replay through the same validity checks as any other.

Whitelisted point-event sections capture fixed artwork under ordinary point Containers inside one retained group. A vertical timeline zoom changes only their Y anchors, computed from immutable event times; it does not scale marker shapes or strokes. Updates require a detached, valid group and unchanged linear transform, and validate every position before mutating any. Unsupported/spanning ranges retain their existing invalidation path; a refused update rebuilds that section. Name anchors are recomputed without mutating previously published names. Point Containers share group release/recycling and pin ownership, including one-shot capture retirement. Actual-scene tests permit only reviewed sparse marker-edge rounding against the former direct draw; reuse versus fresh capture, support, interior pixels and semantic state remain exact.

Supported event-connection sections instead own persistent [`EventStrokeMesh`](../src/rendering/eventStrokeMesh.ts) geometry and position/UV/index buffers. Zoom expands a nearby lane/time centerline at the current device scale and fixed stroke width, stages every section member, then updates the existing buffers only if all double/Float32 non-overlap certificates pass. Queued or stale-owner groups cannot update. Mixed sections, uncertain geometry and unsupported styles keep the ordinary fallback; live previews are unchanged. Camera/mask sides remain separate translucent draws. Group release, context loss and disposal destroy these owned buffers rather than returning them to the immutable path cache. Prepared centerlines live in the existing entity-keyed WeakMap: only the latest preparation is kept, but live entities can keep that CPU metadata after their native groups are released.

Connector body fills use a nearby origin and fixed reference-time path/gradient coordinates. Cached paths and gradients include the current `SlideInfos` reference in same-beat guide validity, so slide-membership changes refresh their alpha and geometry. `fillConnectorBody()` borrows immutable geometry from the existing path cache and submits a separate transformed node, preserving earlier queued submissions. Power-of-two physical-resolution buckets include the current Y stretch and retain the existing curve-error target; this is not a cache of preset zooms. Nonfinite, singular, sheared or excessive scales use the ordinary fill. Current-scale body clipping, outlines and fake-marker ordering remain unchanged. Connector LOD and event-stroke tests qualify only reviewed sparse edge/silhouette differences from the old drawing path; reused versus fresh output, alpha, reference-flat interiors and support-neighborhood guards remain strict. These qualifications are not permission to widen unrelated visual tolerances.

Composed stages are retained in [`stageSurface.ts`](../src/editor/canvas/stageSurface.ts) as tiles of chart time, 128 CSS pixels tall at the current zoom, packed once into device-scaled triangles and drawn straight into the chart. A scroll or pan changes only each tile's offset; there is no stage texture and no motion window. A tile is built when it first comes into view, and while the view moves, one tile ahead is built in a frame that built none, so steady scrolling builds at most one tile a frame. A jump still builds every tile in view at once. Tiles reach a quarter view width past each side of the view they were built for; a pan beyond that builds them again around the view. The stage set, tempo, zoom, device scale, lane division, stage scope and renderer owner are the cache key: a change to any of them, a stage or BPM edit, a preview of one, context loss and Basic release every tile. The stage colors do not depend on the theme. Each tile samples curves from its own edges, so a tile edge is an ordinary slice boundary: shared edge vertices are identical and leave no seam. Compared with one draw of the whole view, curved edges and slanted dividers can move within the 0.01-lane sampling tolerance, and where two stages overlap a border's butt cap crossing a tile edge can blend before the next tile's earlier stage. Neither is visible. Slices the triangle stream cannot represent are kept as ordinary draws in their painter position and redrawn each frame. A build appends each slice's fill, borders and clipped dividers straight to the tile's triangle stream and reuses the clipper's storage: zoomed out, a tile can hold over a thousand divider strokes, and arrays allocated for each stroke made builds several times slower.

[`notes.ts`](../src/editor/canvas/notes.ts) separately retains complete note-body sections, with the existing visible runs as a fallback. The domain cache owns these runs, while `WebGLDrawContext` owns their native groups. Runs borrow atlas regions without extending their validity or taking persistent leases, and each replay registers source readers again. Warm sections touch their distinct artwork before miss allocation; preparation and visible name placement still run each frame. Vertical timeline zoom can update only a detached run's Y positions from absolute note times, preserving Sprite/artwork identity and fixed size. Invalid regions, queued groups or changed linear transforms refuse this update atomically. Changed artwork, membership, order, other transforms, relevant hover/activity or renderer ownership invalidates a run. A section with anchors or ticks keeps two variants, idle and recently active (their outlines), so the start and end of a gesture replay instead of rebuilding. Other sections keep one variant for both. Eviction never takes the variant a shown section uses. Changes, context loss and disposal release native resources.

The main pane's off-screen note badges are DOM, over the chart, and follow the same split. A note's side and slot change only with the lane axis, the timeline zoom and the chart. [`slotOffscreenNotes`](../src/editor/offscreenNotes.ts) groups the notes off a side by slot, over whole 8-beat chunks of keys around the pane, so a scroll regroups them once a chunk. Each frame `placeOffscreenSlots` only places those slots: the same badges, in the same order, as `groupOffscreenNotes` gives per note. The elevation editor and short bands still use `groupOffscreenNotes`. A slot whose notes are unchanged keeps its badge object, so Vue re-renders only the badges that change. Badges still mount and unmount where their slots pass the held badges at the edges.

## The preview's combo

Show Combo (`previewShowCombo`) draws the combo of a perfect play in the preview's own frame, so both hosts draw it with the same code. [`combo.ts`](../src/preview/engine/combo.ts) keeps each chart's combo times, from the classification that Statistics uses ([`scoring.ts`](../src/levelData/scoring.ts)), and a binary search gives the count at a frame's time: the notes the frame shows as passed. [`comboDraw.ts`](../src/preview/engine/comboDraw.ts) draws it last in `renderPreviewFrame`, with the plain `draw`, so a selection never outlines it.

**Layers.** From back to front: the background (pass B), the stage, connectors, notes and slot glow (layers 1 to 23), hitboxes (24), particles (100), then the combo's label and number at layer 200 (`LAYER_COMBO`). The selection outline and the panel's DOM are above the preview canvas.

**Texture slots.** The renderer ([`gl.ts`](../src/preview/gl.ts)) samples one of four textures per sprite, chosen by `Sprite.texture`: 0 the skin, 1 the particle, 2 text and 3 the background. The fragment shader mixes slots 0 and 1 as before. `setTexture` uploads a whole atlas. `reserveTexture` allocates a transparent texture with linear filtering, and `setTextureRegion` uploads a bitmap into part of it, with the atlases' premultiplied upload.

**The glyphs.** The digits are Outfit SemiBold and the label is Outfit Bold. Their outlines are baked into [`comboGlyphs.ts`](../src/preview/engine/comboGlyphs.ts) by `scripts/bake-combo-glyphs.py` from a pinned font file. The bake keeps the coordinates that instancing and overlap removal produce, and measures each glyph's bounds and flat edges on the path data it writes. No font is loaded, so every locale and thread draws the same label.

**The raster.** [`comboType.ts`](../src/preview/engine/comboType.ts) lays out the combo from the buffer's size alone: sizes are fractions of the 16:9 field's height, and the number is centred on the engine's combo anchor by its tabular box, so it moves only when it gains a digit. At rest, every flat edge, baseline and quad corner is on a whole device pixel. The label's ink box is centred on the number with a small optical shift, and its fractional position is drawn into its image. The label and the number are each one `Path2D`, stroked once and filled once on a CPU `OffscreenCanvas` (`willReadFrequently`) in the thread that draws. Touching outlines in one path are covered once. In Chromium, the CPU raster draws the same bytes on the main thread and in a worker. In Chromium, a glyph's edge pixels can change by a few levels when another glyph in the same row changes, because the coverage of a row depends on every edge that crosses it.

**The cache.** Each renderer keeps its own combo state, so a new context, an Antialiasing change or a handover starts afresh. The text texture's layout depends only on the figure height, with room for 7 digits: a count change uploads the number again into the same region, and the label is drawn again only when its position within a pixel changes. Any allocation, such as for a new size or an eighth digit, draws both images again before the frame draws.

**Motion.** After each increment, the number scales from 1.08 to 1 over 140 ms of chart time, with a cubic ease-out, about the centre of its tabular box. Paused frames are at rest. A frame depends only on its time, whether it is paused and its size, so playing to a time and seeking there draw the same pixels (`previewCombo.spec.ts`).

## Native fonts are the Canvas2D exception

[`createFontContext()`](../src/rendering/textRaster.ts) is the centralized Canvas2D entry point for browser font metrics, whole-string shaping and immutable font sprites. This preserves system fallback, language-specific glyphs, kerning and color emoji. The editor scene, clipping and compositing remain WebGL. Do not replace these sprites with per-character quads or an unrelated font engine without a separate typography decision.

`PreparedTextRaster` retains layout and a raster-cache key, not an extra bitmap reference. Font loading invalidates metrics/raster generations; direction and language are part of style validity. A context resolves an inherited `direction` from the canvas's computed style only when the page's `dir`, `lang`, the canvas's `dir` or its connection changes, because reading a computed style forces a style recalculation after any DOM change, such as the preview clock's text; a `direction` set only by a stylesheet rule on the canvas goes unseen until one of those changes. General text uses 1/64-device-pixel origins. Grid labels deliberately snap the final raw baseline anchor to an integer device pixel, with at most 0.5-pixel displacement; note/tick geometry remains unsnapped. Name sprites already use integer device anchors. These policies must remain explicit in visual tests.

Numeric event annotations use the same final integer-device-anchor policy in prepared, live-preview and overflow paths. Prepared labels and local ease glyphs survive vertical timeline zoom by recomputing placement from cached event time and current UPS (timeline units per second); font, BPM, scale, matrix, surface and ownership invalidation remain. Their markers and ease glyphs keep continuous geometry. Name decluttering suppresses only overlapping ordinary names and preserves selected/hovered labels; the explicit group/stage focus-hide settings take precedence and hide all corresponding text while a specific scope is focused.

The selected name contrast uses a native whole-string 0.5-CSS-pixel black outline. `getOutlinedNameRaster()` preserves its shaping, anchor and alpha when a name exceeds the ordinary sprite cap, with viewport clipping before allocation. The fallback source is released through queued-reader flushing after each draw; no obsolete per-fill contrast clipping remains.

## The minimap is the second Canvas2D surface

The minimap strip (`src/editor/minimap/`) draws its content with Canvas2D, a second exception beside the fonts. The chart is Pixi on one WebGL2 root per canvas; a second root for a narrow strip would be another context, renderer, loss path and set of pools. The strip draws about 2,300 flat shapes on coconut, and Canvas2D records them in under a millisecond.

- **What it reads.** The committed `state` (the peeked state while viewing history), never `sceneState`. A tool dialog's preview or a Composed drag preview reaches the strip at its commit.
- **What it draws.** What the chart pane draws. One rule, `entityDrawState` (`canvas/ordering.ts`), decides for the chart, the strip, both mark layers and History's change marks whether an object is hidden, dimmed or drawn at full strength, from the group and stage scope, the type switches and Show Other Objects (`entityVisibility` in `scope.ts`). Hidden notes and bodies are left out; dimmed ones are drawn at the chart's `DIM`. The range stays the whole chart's, so hiding never rescales the strip. `contentVisibility` (`minimap/visibility.ts`) is `entityVisibility` reduced to what the strip draws, notes and bodies. Switches for types the strip does not draw keep its identity, so they redraw nothing.
- **Positions.** Lanes −6 to 6 are linear over the central 80% of the width; lanes beyond them are compressed into the margins and never clipped. In Composed, `getComposedLayout` gives each note and connector span; otherwise the authoring `left` and `size`. One module (`mapping.ts`) holds this, and the painter, the overlay, the input and the mark layers read it.
- **Updates.** Change detection is an identity diff of `store.grid.note` and `.connector` and of each key's bucket (a transaction copies a bucket on first write, so an untouched bucket keeps its identity). Changed keys become bands. A band repaints whole items in the canonical paint order (gutter rules, connector bodies, notes) into the back buffer and copies its rows to the front. It uses no canvas clip, because a clip would change the antialiased edges of slanted bodies. A band then gives exactly the pixels of a full redraw. A change over 256 entities, or over a third of the height, is a full redraw instead. A BPM edit moves the range without touching the grid, so the range is converted to time on every pass.
- **Full redraws are sliced.** They run in animation-frame slices of 2 ms of recording into a CPU back buffer, and each slice forces its rasterisation with a 1×1 readback so the cost lands inside the slice, not in the swap. The front canvas gets one blit. Both canvases are CPU canvases (`willReadFrequently`), so band copies and blits rasterise predictably. A geometry, range, layout, tempo or visibility change cancels a running job; other edits wait for it and land as bands. A visibility change is a full redraw, read once for the whole job.
- **Scale.** At most 2, and low enough that the backing store is at most 4,096 rows. A resize or a pixel-ratio change starts a full redraw 100 ms after the last change; the old image is stretched by CSS meanwhile.
- **Marks on layers of their own.** Each kind of mark over the content has its own canvas, inputs, schedule and counter (`useMinimapLayer` in `layers.ts`), so one kind never repaints another: History's change ticks (`changePaints`) and the selection (`selectionPaints`). Both canvases are CPU canvases (`willReadFrequently`), like the content's, and exist only while they have something to draw.
- **The selection layer follows the content's image.** The lift is drawn on the notes, and the content canvas can lag the state: a full redraw is sliced, a running job keeps going through later edits, and a resize stretches the old image for 100 ms. The pipeline publishes what its front canvas shows (`drawn`: the note grid, tempo, layout, visibility, range and geometry) at every swap and band pass. The selection layer is drawn only while `drawn` matches the shown state and the mapping. History's ticks sit on rows, not on notes, so they wait only for the visibility. They never mark a change the image does not yet show, or leave out one it still shows. The layer repaints in the frame that `drawn` changes, and in the next animation frame after the selection or the mapping changes. A paint that would draw what is already there is skipped. When the front image changes to one the marks were not drawn for, the layer is hidden until a matching paint. During a resize the marks stretch with the content and are not repainted.
- **Context loss.** While a content canvas's context is lost, its pixels are gone: the pipeline draws and publishes nothing, `drawn` is cleared so the selection layer stays hidden, and a full redraw starts when the context is restored. A mark layer whose own context is restored paints again.
- **Zero work while moving.** A wheel scroll, playback with Follow and a held chart drag paint nothing: the box and the cursor move by transform, written by one watcher outside the template. `minimapStats.paints`, `.changePaints` and `.selectionPaints` (read through `editorTest.appImport`) stay unchanged over those, with a selection shown, and `tests/browser/minimap.spec.ts` checks it.
- **Hidden means free.** The strip is unmounted when off, so its watchers, observers and canvases do not exist.

## Streamed video output

`src/exportVideo/codecs.ts` owns encoder configurations and support probes. Keep one probe instance per page. Its cache includes every configuration field; the availability instance resolves the current selection and every supplied choice on each update. A pending or superseded selection cannot enable export. H.264 tries High, Main and Baseline, at the lowest level that meets frame size, dimension, processing rate and bitrate limits. WebKit gets Constrained Baseline only. In other profiles its encoder buffers more frames than the WebCodecs encode queue allows, so encoding stalls ([WebKit bug 324827](https://bugs.webkit.org/show_bug.cgi?id=324827), fixed by [WebKit pull request 74602](https://github.com/WebKit/WebKit/pull/74602)). A trial encode cannot catch this, because it flushes after three frames. `createExportServices` passes the engine from `src/platform/detect.ts`. A support query that throws counts as unsupported for that configuration; only a refused configuration is cached, and the next candidate is tried. A configuration that `isConfigSupported` accepts must also pass a trial encode of a key frame and two delta frames, made as raw YUV frames. The output goes through the export's video adapter and an in-memory mux (`worker/trial.ts`, which Export Video loads with the dialog). An encoder error, output the adapter cannot use at all or a muxer error makes the configuration unsupported. Output the adapter repairs passes. Firefox's H.264 encoder repeats the SPS NAL header byte, so Firefox exports WebM. Trials run one at a time. Their results are cached by the whole configuration, bitrate included. Callers share a trial or an AAC measurement in progress. A caller leaves when its signal aborts, as on Cancel, and an availability update leaves when a newer update replaces it. When the last caller leaves, a queued trial is skipped, and started work stops and closes its codecs. Started work whose last caller was replaced by a newer update runs to its end instead, and its result is cached. Closing the dialog stops that work too. Stopped work and a failed AAC measurement are not cached. Each availability update resolves the selection first and publishes it, so Export does not wait for the offered choices. The offered choices follow, with trials only at the selected size and frame rate. Other choices use `isConfigSupported` alone. With sound selected, the audio configuration is probed first, so a browser without AAC runs no H.264 trial. For MP4 with sound, a selection with trials also measures the AAC delay. When it cannot be measured, MP4 stays available, for Automatic too: the export places the sound with an estimate of one frame, 1,024 samples, and has the `audioSyncEstimated` warning. The measured delay stays unknown, and the estimate is never cached as a measurement. Automatic retains the selected sound when falling back to WebM. The dialog also checks render sizes against the export worker's WebGL viewport, texture and renderbuffer limits through `fitsGraphicsLimits`. Until those limits are known, Export waits. Limits that cannot be read leave every size available; a size that cannot be drawn fails the export at its first frame. Resolution choices must pass both these checks and the encoder probes. With sound selected, one more choice probes the selection without sound.

`src/exportVideo/mix.ts` consumes the shared sound plan and decoded buffers. It renders ten-second stereo blocks at 48 kHz, with 128 ms of guard audio at each continuation. Voices keep their source position, loop phase and envelope across contexts. Continuing sources resume at an offset aligned to both sample rates within the guard. Volumes are linear, fades multiply the mix and the final samples are clamped. The iterator renders only the next requested block. `timing.ts` derives timestamps from frame and sample indices and divides blocks into units of at most 100 ms.

`src/exportVideo/worker/encode.ts` defines the muxer's input as `MuxInput`: audio or video packets with microsecond timestamps, durations, bytes and decoder configurations, followed by an `audioEnd` item. Before the first frame, `worker/encoderColor.ts` measures the encoder's RGB-to-YUV conversion. It encodes colour stripes captured from the export canvas, then the same stripes as YUV frames converted with BT.709 and BT.601 at full and limited range, and decodes them all with one decoder. Each decoded frame belongs to the input nearest its timestamp, within half a frame; a frame as near two inputs, or a second frame for one input, means no measurement. Each decoded frame is drawn once and read before it closes. A candidate is measured when its frame decodes, on average, within 2 levels of the captured frame and every other candidate is more than 2 levels further away, even when it agrees with the encoder's report. A failed measurement means none. Cancel ends it at once and closes its codecs. Firefox's VP9 encoder converts with BT.601 limited range and reports BT.709, so its files declare `smpte170m`. Each colour field of the file takes the measured value (matrix and range only), then the value the bitstream declares, then the encoder's report. The report only fills fields the bitstream leaves absent or unspecified. `worker/avcColor.ts` writes the result into every SPS, and `worker/vp9Color.ts` writes the matrix and range into every profile 0 YUV key frame, including key frames without metadata. The MP4 `colr` box describes the SPS as written. The WebM `Colour` element leaves the matrix unspecified, so only the VP9 headers declare it and mediabunny does not rewrite them. Colour never fails an export. Unreadable colour fields in an SPS or the first VP9 key frame pass unchanged, and the file declares no container colour. An SPS that cannot be rewritten passes unchanged with its own colour. An MP4 file whose range is unknown has no `colr`, because mediabunny would declare limited range. `createVideoPacketAdapter` places each chunk on the frame nearest its timestamp and gives the packet that frame's timestamp and duration. This absorbs WebKit's timestamps, which are 1 µs early from about 4.03 s ([WebKit bug 321880](https://bugs.webkit.org/show_bug.cgi?id=321880)). Packets keep their encoded order. Video starts at the first key chunk with a usable configuration, carried by that chunk or by a skipped one before it; earlier chunks are skipped. That chunk goes on frame 0, with `timingReassigned` when its time was not frame 0 or earlier chunks were skipped. A chunk whose frame is outside the clip, already taken or not after its group gets the frame after the latest one, with the `timingReassigned` warning. A key chunk's group starts after every earlier frame. Frames of the clip without a chunk give `framesMissing`. The track holds at most `videoPacketBound` packets: the frames and a tenth more, at least 120 more. A later configuration may repeat the first. For H.264, the codec string, the displayed size and the initialization are compared without colour, so an SPS that differs only in its VUI colour fields is the same. For VP9, only the displayed size is compared. The muxers keep the first configuration, so another H.264 initialization or size ends the picture there, as do the packet bound, a video encoder error, a lost graphics context and a frame that cannot be drawn or captured. The file keeps the video before it, with the `pictureStopped` warning, and the sound goes on. The export fails only when no video was kept. `worker/videoInit.ts` reads that initialization. An H.264 description must be a configuration record whose SPS and PPS entries are complete, with their own NAL headers, and whose first SPS has the record's profile. Reading the SPS's size and colour is optional; an SPS that cannot be read is compared whole. Firefox's encoder repeats the NAL header byte, so its descriptions fail this check. The profile may differ from the requested one, and the container takes the record's codec string. The displayed size comes from the SPS, after cropping, or from a VP9 key frame's header, then from the reported coded size, then from the request. The container records it, so a coded size padded to whole macroblocks is recorded as the SPS crops it. A size other than the requested one gives `resolutionDiffers`. VP9 output without a configuration takes the requested codec. Every packet then passes through the track's colour step (`createVideoColor`). AAC descriptions are normalised to AudioSpecificConfig in one place, `normalizeAacDescription`. A missing, truncated or malformed description, or one with object type 0, becomes `11 90`, the requested AAC-LC at 48 kHz in stereo; the delay measurement decodes with the same. Every audio encoder receives 1,024 silent samples before clip time zero, in the same call as the first clip samples. Safari's encoder encodes the first 1,024 samples it receives as silence ([WebKit bug 328491](https://bugs.webkit.org/show_bug.cgi?id=328491)). According to [Mediabunny issue 444](https://github.com/Vanilagy/mediabunny/issues/444), Safari still loses the start of the clip when the silence is sent in a call of its own. The lead-in also gives the MP4 an edit list when the encoder has no delay. AAC input ends with 1,024 more silent samples, in the call with the last clip samples. Chromium on Android drops the last packet of AAC output. With the tail, that packet contains only silence. AAC delay is measured by encoding and decoding an impulse. The result is cached by the complete configuration. Opus delay comes from its header.

Audio packets are placed end to end by their durations, rounded to samples, with the silent lead-in and encoder delay before zero. A packet without a duration takes the codec's: the AAC frame length from the AudioSpecificConfig, or the Opus frame size and count from its TOC byte. Sound that ends more than 96 samples (2 ms) short of the clip has the `soundStopped` warning. Ending up to 96 samples short is taken as an error in the delay, not missing sound, and reported as no padding. Every Opus packet reaches the muxer, including final padding. AAC packets that start at or after the end of the clip are left out, and the packet that crosses it is shortened to end there. The first packet carries the audio configuration; AAC without one gets the requested one. A later one may repeat it, in another wrapper or without its description. Any failure of the sound fails the export with `AudioFailure`, the `audio` reason: mixing, configuring, feeding or encoding, a duration that cannot be read, an Opus header that cannot be read, no encoded sound, or a change of the sample rate, channels or normalised description. The Opus header's pre-skip includes the lead-in. `AudioTiming` reports accounting only. The final `paddingSamples` counts the samples after the clip that reach the muxer, so it is 0 for AAC. The loop counts written audio on this timeline without subtracting the start offset again. The feeder checks contiguous input and exact length before encoders are flushed.

Mediabunny 1.65.0 is unmodified and bundled in the export worker and the trial chunk. MP4 uses `fastStart: 'reserve'`, so `moov` comes before a `free` box and `mdat`, and the tracks interleave in `mdat`. The video bound is `videoPacketBound`. The AAC bound (`aacPacketBound`) covers the lead-in, the delay, the clip and the tail in 512-sample packets, half the shorter AAC-LC frame, and 64 more. The adapters end a track before its bound. WebM uses a seekable target. Both stream positional writes in 16 MiB chunks. Finalising the muxer does not commit the file; the worker commits after its checks. The memory route uses `BufferTarget` without a size limit. Where the allocation throws, running out of memory fails the export as `memory`; a browser can instead end the page.

Negative timestamps produce an MP4 edit list. It starts after the lead-in and the encoder delay and presents exactly the clip. MP4 roll groups for audio specify one preceding AAC packet for decoding after a seek. WebM derives `CodecDelay` from the negative first audio timestamp and shifts block timestamps by that delay. The Opus header keeps the raised pre-skip, and `SeekPreRoll` is 400 ms. WebM writes no `DiscardPadding`; its block timestamps have millisecond precision. WebM keeps the final Opus padding, and the file's duration may include it and container rounding. The adapter reports the padding count. Playback alignment depends on the player's handling of container timing.

`src/editor/exportVideo/destination.ts` prepares an accepted pick or a staged file, or selects the memory route when staging is refused: SecurityError (Firefox private windows), UnknownError (WebKit without a storage path, as in Safari Private Browsing) or NotSupportedError. The dialog knows the route before an export from the limits worker, which opens the origin private file system and looks for `createSyncAccessHandle` without creating a file, and from an earlier export in the page that took the memory route. Above `VIDEO_MEMORY_WARNING_BYTES` of estimated output on that route, the dialog warns, and Export stays available. The resolved format determines the destination's file name, extension and MIME type and the usage event's format. The worker opens its target before encoding. When it cannot open a staged file for writing (no `createSyncAccessHandle`), nothing has been encoded. The job removes the staged file and continues on the memory route with the same worker. Quota and I/O failures keep their own errors. A destination that arrives after Cancel is discarded. Its result leaves target ownership with the caller. `report.ts` builds the usage event's raw payload from settings and explicit end measurements. The dialog records the `exportVideo` event once per attempt, after its outcome is known. Work time is captured before waiting for delivery. The analytics catalogue converts sizes and lengths to its existing ranges.

The position-addressed targets in `src/exportVideo/worker/target.ts` write chunks through a picked file's writable stream or an OPFS sync access handle. They support rewriting headers without collecting the whole output in memory. The caller awaits each write and closes or aborts the target before releasing its destination.

`src/editor/save/videoPick.ts` uses the shared pick session. The job prepares its assets and resolves its encoder configuration before the picker opens. Changed sound effects require a fresh job before preparation. If activation expires, the existing Ready press supplies another gesture. Every pick is accepted while it remains empty. Matching project bindings and remembered export destinations are revoked under `nse-bind`; streaming starts after the hold is released. Before committing, the target must still be empty with the modification time read at the pick. When reading the file is not allowed, as on Android, the commit goes ahead without this check. Cancellation or failure before the commit aborts the swap and removes only that unchanged empty file. A file that cannot be read is left in place. The read-to-close and read-to-remove windows can still race another writer.

`platform.videoOutput` owns staged files under `export-video/`, each protected by `nse-export-video:<id>`. The page sends the worker only the file name, because Safari cannot send file handles to a worker; the worker opens the file in `export-video/` itself. The worker closes its sync access handle before the owner removes a cancelled or failed output. A file remains locked while Ready is shown. After a successful delivery, `endReady()` starts the hand-over's ten-minute retention; an undelivered file is removed at once. Call it only after any required discard confirmation. Downloads use the existing hand-over, and shares use the video's MIME type. A dismissed share keeps the file available.

The maintenance runner sweeps unlocked staged files before checking storage pressure. A deletion attempt releases ownership even if it fails, so a later sweep can retry. The sweep never reads project media or History. Web implements staging in OPFS, the mock keeps it in memory, and native leaves `videoOutput` absent.

### Export jobs

`src/exportVideo/job.ts` owns one chart snapshot and its export. The editor supplies copied assets, audio buffers, a destination and a worker. `copyExportAssets` copies the shown skin, particles and background through their current preview host. The worker uploads the copies and closes them. The renderer keeps the background's uploaded dimensions separately from its bitmap.

When browser storage is available, an export writes its resolution and render scale to `localStorage` under `exportVideoRunning.<id>` after acquiring its job lock. It removes that marker at every end and on `pagehide`. The dialog removes abandoned markers under their job locks and remembers the last interrupted choices. After an interruption, it opens with choices from the last completed export, or defaults if no export completed.

The dialog reads `state` and receives changes through `changed`. The phases are `setup`, `preparing`, `exporting` (frame count, fraction complete and ETA in seconds), `cancelling`, `finishing`, `ready`, `done`, `failed` and `cancelled`. `preview(time, size)` returns a bitmap that the caller closes; a queued request replaced by a newer request returns no bitmap. `configure(settings)` changes the setup before `start()`. A failed preparation, for a view or an export, is tried again by the next one, and a failed view does not stop an export. Ready and Done carry the export's warnings (`ExportWarning` in `warnings.ts`), and a delivery keeps them. Cancel stops preparation or encoding; it is refused during the commit and in Ready. At Ready or Done the job releases its worker, and Ready keeps the file, not the in-memory route's buffer. `deliver()` keeps Ready available for retries, also after a failed share. Call `endReady()` only after confirming the discard of an undelivered file. `dispose()` cancels work before the commit, waits for an active commit and releases the worker. A staged destination keeps its lock through Ready and the platform's retention period.

The Export Video dialog (`src/editor/exportVideo/dialog.ts`) keeps one job in setup, whose worker draws the frame view, and starts that job when Export is pressed. Every attempt ends with a new job for the views, since a job runs once. The dialog's playback plays the snapshot with its own sound settings on Play's audio context (`startClipPlayer`) and never moves the editor's cursor. `src/editor/exportVideo/export.worker.ts` installs `openMuxOutput` as the page worker's muxer.

`host.ts` and `worker/export.worker.ts` carry view requests, audio blocks, progress and cancellation. A worker entry calls `installExportWorker` with a function that opens its packet sink and target. The sink accepts `MuxInput` from `worker/encode.ts`; its `add` resolves after writing that packet, and `finalize` does not commit the target. The worker awaits the commit separately. This keeps the container implementation outside the frame loop.

The worker uses the preview renderer at a logical height of 540 pixels. An optional composite target receives the background and foreground, then an export pass applies fades before downscaling. A frame that fails the graphics check after drawing is still captured, with the `framesIncomplete` warning. A frame that cannot be drawn, such as one whose render target cannot be made, ends the picture there. A lost context ends it at the next capture, without waiting for restoration. With no frame kept, the job fails as `graphics`, or `background` while the page is hidden. Black frames are valid. A progress image that cannot be made leaves the numeric progress. After a Cancel, only a failed removal of the destination is reported. A failed export keeps its own error; Error Details add a refused first attempt and any failed cleanup, each once, and keep them across the worker boundary.

The loop gates each video frame and each 100 ms audio unit on encoder input consumption, queued packets and a one-second lead in clip time. It counts submitted and written work per track, excluding audio trims from playable audio. Those counts never gate input on encoder output. Encoders in quality mode may retain frames until flush. A single drain awaits each packet write; finalization waits for audio submission, both encoder flushes and the last write. Cancellation and the first error settle the waits.

The browser hook at `window.editorTest.exportVideo` runs the job through real encoders and an OPFS target. By default, its test sink records packets and decoder metadata and checks that each video packet has a whole frame's timestamp and duration, once, the first packet is a key frame with the only configuration, and dimensions and audio trims, without writing a media container. The hook returns the export's warnings, which say what the file lacks. With `mux: true`, it uses the real muxer and returns the file bytes. `tests/browser/exportVideoMux.spec.ts` checks decoded frames, audio alignment and container timing. `exportVideoAudio.spec.ts` checks mixing and encoder timing.

## Pinned Pixi seams and upgrade gate

The portable package pins **Pixi 8.22.0** exactly. `postinstall` runs [`patch-pixi-default-batcher.mjs`](../scripts/patch-pixi-default-batcher.mjs). It validates the version and full original hashes of both ESM/CommonJS files before writing; partial application or drift fails. Re-running is a no-op. `--check` validates already-patched output without writing. Release staging invokes that read-only mode and checks package/lock pins before publishing patch notices.

The patch makes the initial default batch use Pixi's registered batcher, enabling the editor's axis-line coverage extension. This is an install-time change, not an intercepted GL call.

An upgrade must re-audit more than that patch:

- [`pixiAxisLine.ts`](../src/rendering/pixiAxisLine.ts): default six-float packing, texture/rounding fields, shader bits, group alpha and shared shader lifetime. Normal sprites/meshes must remain unchanged in mixed batches; retained fractional translations must move coverage correctly.
- [`pathTriangles.ts`](../src/rendering/pathTriangles.ts): exported-but-internal `buildContextBatches` / `GpuGraphicsContext`, triangle topology and borrowed scratch batches. Copy required data before destroying scratch; never retain pooled arrays. The native stroke-strip certificate depends on those exact topology invariants.
- [`pixiRectClip.ts`](../src/rendering/pixiRectClip.ts): instruction/effect pipes, batch barriers, root-versus-texture Y direction and target resolution.
- `RenderingResources`: explicit RenderTarget/MSAA lifetime, extraction, restored texture bindings and partial-init teardown. `RenderingScheduler` must still implement the scheduler behavior expected by Pixi GC. It relies on GC's tasks only marking a pass due, on `postrender` running a due pass (the scheduler calls `postrender` at idle time), and on GC's `maxUnusedTime` age rule.
- Retained note bodies and point events: consecutive painter order, detached atomic position updates with fixed artwork, current-frame atlas validity, reader registration on every replay, and group/Sprite/point-Container release after invalidation, context loss or disposal. Keep names and preparation live, including preview and overflow fallback; preserve the narrow point-edge fixture qualification and exact fresh-capture/semantic checks.
- Persistent event strokes and connector fills: pinned `buildLine` topology, double/Float32 strip certification, atomic section staging, owned-buffer destruction, immutable shared fill geometry and physical-resolution bucket quality. Preserve separate-side alpha and the reviewed sparse-edge fixtures, including queued submissions and fresh-capture equality across arbitrary zoom values.

Use a clean installation and run patch-guard/release tests, type checks, and the focused native-oracle, lifecycle, scheduler, stage-surface, label-source, mixed-axis and stroke-topology tests. Include context loss/restore, destroy/recreate, queued-source mutation/release, idle GC resume and explicit rejection when WebGL2 is unavailable. Keep the supported browser-engine and mobile-device matrix. Then compare real dense charts and performance under identical viewport, DPR, activity, scroll trajectory and CPU conditions. Successful compilation or patch application alone is insufficient.
