# Stats

Usage statistics for the web editor: a self-hosted [Umami](https://umami.is) on one small EC2 instance. The editor’s sender is `src/analytics/`, and `docs/analytics.md` describes what it sends. This page runs the server. Read `../README.md` first for the accounts, the set-up and the cost review.

## What runs

| Part         | Detail                                                                                                                                                                                       |
| ------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Instance     | Ubuntu 24.04 LTS arm64. Prod `t4g.small`, dev `t4g.micro` with 1 GB of swap. Default VPC, one public subnet, Elastic IP, IMDSv2 only                                                         |
| Network      | Port 443 in, nothing else. No SSH: access is Session Manager. Certificates come from the TLS-ALPN-01 challenge on 443, so port 80 stays closed                                               |
| Containers   | Caddy, Umami and PostgreSQL in Compose, each pinned by digest in `host/images.env`. PostgreSQL has no published port                                                                         |
| Public paths | `POST /api/send`, `POST /api/batch`, `GET /api/heartbeat`. Everything else is a 404, and Caddy keeps no access log                                                                           |
| Dashboard    | Umami’s login is never routed publicly. It is on the instance’s `127.0.0.1:3000`, reached through a Session Manager tunnel                                                                   |
| Data         | One encrypted gp3 volume at `/data`: PostgreSQL, Caddy’s certificates and `secrets.env`. It is retained when the stack is replaced or deleted                                                |
| Secrets      | Umami’s `APP_SECRET` and the database password are generated by `update.sh` on first boot into `/data/secrets.env` (root only). Nothing is in the repository, GitHub or AWS                  |
| Backups      | A weekly `pg_dump` (Sundays, 03:00 UTC) to a versioned S3 bucket, kept 28 days. The instance can add and list dumps, not read or delete them                                                 |
| Nightly job  | `host/nightly.sh` at 03:00 UTC in prod: clears the region and city Umami adds, dumps on Sundays, and checks the last dump, the disk (80%) and a test event. A failure emails the alert topic |
| Patches      | Unattended security upgrades, rebooting at 04:00 UTC when needed                                                                                                                             |
| Recovery     | EC2’s own recovery for a failed system check. In prod, one alarm reboots the instance after 5 minutes of failed instance checks and emails                                                   |

The host files reach the instance by commit. The stack’s `SourceCommit` parameter becomes the tag `nse:commit`. `update.sh` downloads `host/*` at that commit from `raw.githubusercontent.com` (the repository is public), so a deploy never restarts the instance. The user data runs once, at first boot, and does not change.

## Deploy

**Set-up** (once; `../README.md` has the rest): the Environments `stats-dev` and `stats-prod` with `AWS_ACCOUNT_ID`, and the baseline deployed in the account.

Run Actions › Stats deploy, choosing `dev` or `prod`. Prod waits for the maintainer’s approval and refuses any branch but `main`. The workflow assumes `nse-stats-deploy` by OIDC, runs `scripts/deploy.sh`, and ends with a smoke check: `/api/heartbeat` over HTTPS, then the database’s migrations. The same script runs by hand with a profile: `AWS_PROFILE=nse-dev SOURCE_COMMIT=<pushed sha> bash infra/stats/scripts/deploy.sh dev`.

If the first deploy of a stack fails, CloudFormation leaves it in `ROLLBACK_COMPLETE`, and it deletes the empty volume, Elastic IP and bucket it had made (they are `RetainExceptOnCreate`). The deploy roles cannot delete a stack in prod, so delete it with the admin profile (`aws cloudformation delete-stack --profile nse-prod --stack-name nse-stats`), fix the cause, and deploy again. Never delete a stack that has run, because its data volume, address and bucket are then left behind.

Try the whole cycle in dev first (see Dev below). Deploying prod, in order:

1. Deploy it. The first boot takes 5 to 10 minutes.
2. **First sign-in,** through the tunnel (below). Sign in as `admin` / `umami`, create a new admin with a generated password kept in a password manager, and delete `admin`.
3. Create the websites `nse.qwewqa.dev`, `test.nse.qwewqa.dev` and `monitor`. Their ids go in the repository variables the editor and the test site read, and the monitor’s id in the Environment variable `STATS_MONITOR_WEBSITE` on `stats-prod`. Deploy prod again so the nightly job’s test event has its website.
4. Production sends only after the release that publishes the privacy page.

## The dashboard

```sh
bash infra/stats/scripts/dashboard.sh prod    # or dev; then open http://localhost:3000
```

It needs the Session Manager plugin (`../README.md`, step 3) and a profile `nse-prod` or `nse-dev`. The script finds the running instance by its `nse:service=stats` tag and forwards port 3000.

## Upgrades

An Umami, PostgreSQL or Caddy release is a pull request that changes a digest in `host/images.env`. Find a digest with `docker buildx imagetools inspect <image:tag>`; it must be the index digest. Read Umami’s release notes for migrations and `ANALYZE` steps first. Migrations have no down step.

1. The pull request runs `infra-check.yml`, whose contract test starts the new images and checks the sender’s request, the clean-up, a restore and the saved queries.
2. Deploy dev from `main`, send some events, then deploy dev from the branch. Look at the dashboard and run the saved queries. Run `stats-dev-down`.
3. Merge and deploy prod. `update.sh` takes a dump first whenever `images.env` changed.

After a major Umami upgrade the next Sunday’s `VACUUM (ANALYZE)` refreshes the statistics, or run it from a Session Manager session.

**A PostgreSQL major version** keeps its data in its own folder under the volume (`/var/lib/postgresql/18/docker`). Take a dump, change `POSTGRES_IMAGE`, and deploy. The new version starts an empty cluster in its own folder, and Umami creates its tables. Restore the dump into it (below). The old folder stays on the volume as a rollback until it is deleted by hand.

## Operations

All of these name a profile. On the instance (`aws ssm start-session --profile nse-prod --target <instance id>`, then `sudo -i`), the Compose command is:

```sh
cd /opt/nse-stats
dc() { docker compose --env-file images.env --env-file /data/secrets.env --env-file /data/stats.env "$@"; }
```

- **Take a dump now:** `/opt/nse-stats/nightly.sh dump`.
- **Restore a dump.** The instance cannot read S3, so create a link from your machine, fetch it on the instance, and restore:

    ```sh
    aws s3 ls s3://<bucket>/dumps/ --profile nse-prod
    aws s3 presign s3://<bucket>/dumps/<file> --expires-in 900 --profile nse-prod
    # on the instance:
    mkdir -p /data/dumps && curl -fsSL -o /data/dumps/restore.dump '<link>'
    dc stop umami
    dc exec -T db pg_restore -U umami -d umami --clean --if-exists --no-owner < /data/dumps/restore.dump
    dc up -d umami; rm /data/dumps/restore.dump
    ```

    The bucket name is in the stack’s `BucketName` output. CI tests that a dump restores into a fresh PostgreSQL with the same row counts.

- **Replace the instance** (a new image id, or a broken boot). The data volume is the only thing that must survive. Take a dump; then `aws ec2 modify-instance-attribute --instance-id <id> --no-disable-api-termination`, stop the instance, and detach the volume (`aws ec2 detach-volume`, wait for `available`). Change `ImageId` in `stats.yaml` in a pull request and deploy prod. The new instance attaches the volume and finds its filesystem, certificates, secrets and data. CloudFormation then deletes the old instance. The Elastic IP and the DNS record do not change.
  An edit to the template’s `UserData` does not run again on an existing instance, because cloud-init runs it once per instance. A change to it therefore needs this procedure too.
- **Resize the instance.** Change the sizes in the `Sizes` mapping, `COST_PINS` and the cost table in one pull request, and deploy. CloudFormation stops and starts the instance, which takes about a minute.
- **Replace a secret.** `APP_SECRET`: edit `/data/secrets.env`, then `dc up -d umami`. Dashboard logins end, and the day’s visitor hashes change. The database password: `dc exec db psql -U umami -c "ALTER USER umami PASSWORD '<new>'"`, edit `secrets.env`, then `dc up -d umami`.
- **Delete data.** One website: Settings › Websites › Edit › Reset Data. By date, in `dc exec db psql -U umami umami`, followed by `VACUUM`. The tables have no foreign keys, so delete in this order:

    ```sql
    DELETE FROM event_data WHERE created_at < now() - interval '1 year';
    DELETE FROM website_event WHERE created_at < now() - interval '1 year';
    DELETE FROM session_data WHERE session_id NOT IN (SELECT session_id FROM website_event);
    DELETE FROM session WHERE session_id NOT IN (SELECT session_id FROM website_event);
    ```

    There is no automatic deletion. If a limit is set, add these statements to `clean` in `nightly.sh`.

- **A nightly email** names its cause: no recent dump, the disk over 80%, or the test event refused or missing. The log is `journalctl -u nse-stats-nightly`.
- **If the endpoint is down,** the editor is unaffected and events are lost until it is back.

## Dev

Dev exists only while an analytics test runs, in `nse-dev`, and is deleted completely afterwards.

1. Run Stats deploy for `dev`.
2. `bash infra/stats/scripts/dashboard.sh dev`, sign in as `admin` / `umami`, and create the website `local`. Dev is reachable only through the tunnel, so `admin` stays.
3. Point a dev build at it:

    ```sh
    NSE_ANALYTICS_ORIGIN=https://stats.nse-services-dev.qwewqa.dev NSE_ANALYTICS_WEBSITE=<local id> npm run dev
    ```

4. Run Stats dev down. It deletes the stack, the retained data volume and Elastic IP, and the bucket, then runs `scripts/leftover.sh`. “Nothing of stats is left.” means it worked.
5. If the check names a leftover, delete it by hand with the CLI (`aws ec2 delete-volume`, `aws ec2 release-address`, `aws s3 rb --force`) and run `bash infra/stats/scripts/leftover.sh` with the dev profile.

Once the repository variable `STATS_DEV_REAPER` is `on`, Stats dev down also runs every six hours as a reaper. It acts only on a stack over 12 hours old, and it covers only stats. GitHub disables a scheduled workflow after 60 days without repository activity, so re-enable it after a long pause. The $1 budget on `nse-dev` is the backstop.

Each dev deploy needs a new certificate. Let’s Encrypt allows five per identical set of names a week, and Caddy falls back to ZeroSSL after that.

## What the first dev deploy proves

Some permissions cannot be checked without CloudFormation running them. If the first dev deploy fails, look here first:

- `RunInstances` and the tag conditions on the execution role. The root volume is allowed untagged, and `CreateVolume` is tag-scoped.
- The trust policy of `nse-stats-cfn` requires `aws:SourceArn` for a stack. AWS documents that key for other role types, so if the error is “Role … is invalid or cannot be assumed”, keep `aws:SourceAccount` and drop `aws:SourceArn`.
- `iam:PassRole` for the instance profile, which is allowed to EC2 only (`PassedToService`). If the instance profile create is refused, check that condition.
- The Route 53 record-name condition, in both trailing-dot forms.
- First boot: the data volume’s device name, the Docker packages, `snap install aws-cli`, and tags with `:` in their keys through the metadata service.
- The alarm’s reboot action exists only in prod, so the first prod deploy is its first run. Its service-linked role is allowed in the baseline.

## App-side work with no AWS

```sh
docker compose --env-file infra/stats/host/images.env -f infra/stats/host/compose.local.yaml up
```

Sign in at `http://localhost:3000` as `admin` / `umami`, create a website, and start the editor with `NSE_ANALYTICS_ORIGIN=http://localhost:3000 NSE_ANALYTICS_WEBSITE=<id> npm run dev`. `down -v` deletes the data.

## Reading the numbers

- A pageview is an engaged visit: one where the user clicked, pressed a key, touched or scrolled. Loads that never interacted are not counted at all, so the totals undercount loads by design.
- Count visits from pageviews and durations from `visibleTime`. Ignore Umami’s visit duration and bounce rate, which are wrong for this client.
- Umami’s unique visitors are visitors per day, because the salt rotates daily.
- The saved queries in `queries/` answer the usual questions. Each takes the website’s id:

    ```sh
    bash infra/stats/scripts/query.sh prod infra/stats/queries/commands.sql <website id>
    ```

    `visits.sql` visits per day by country, `commands.sql` commands by use and visitors, `saves.sql` Save outcomes by target and reason, `startup.sql` startup time by how the visit began and the chart size, `frames.sql` long frames per playback second by preview host, and `settings.sql` the common setting values. The contract test runs all of them against Umami’s real schema.
